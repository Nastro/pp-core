# Шаблонизатор: Twig и миграция со Smarty 2

Начиная с версии 4.0.0 клиентский движок шаблонов — **Twig 3** (`TwigLayout`).
Smarty полностью удалён из ядра: ни рантайма, ни плагинов, ни фолбэка.
Проектам, которым нужен Smarty, следует оставаться на ветке 3.x.

## Выбор движка через DI

По умолчанию, без какой-либо конфигурации, используется
`PP\Lib\Html\Layout\TwigLayout`. Проект может подменить движок, определив в
`app/config/services.yml` **публичный** сервис с id
`PP\Lib\Html\Layout\LayoutInterface`:

```yaml
services:
    PP\Lib\Html\Layout\LayoutInterface:
        class: App\Layout\MyCustomLayout
        public: true
```

`PXEngineIndex::initLayout()` заберёт сервис из контейнера; сервис обязан
реализовывать `PP\Lib\Html\Layout\UserLayoutInterface`.

Не забудьте сбросить кэш контейнера (`CACHE_PATH/container.php`) после
изменения `services.yml`.

## TwigLayout

- Шаблоны ищутся в `local/templates/`, затем `libpp/templates/`,
  расширение `.twig`. Легаси-имена `.tmpl`, приходящие из PHP-кода
  (`$layout->html('misc/pager/pages.tmpl')`), прозрачно переписываются
  в `.twig`.
- Автоэкранирование выключено, неопределённые переменные не являются
  ошибкой — так же, как было в Smarty 2 (важно для конвертированных
  шаблонов).
- Неизвестные фильтры и функции Twig резолвятся в глобальные PHP-функции
  (`{{ x|quot }}`, `{{ smarty_file_exists('a.twig') }}`) — аналог
  фолбэка модификаторов Smarty 2 на PHP-функции.
- Smarty-совместимые фильтры (`smarty_escape`, `smarty_default`,
  `smarty_replace`, `cat`, `strip`, `date_format`, `regex_replace`,
  `truncate`, `isset`, `empty`, ...) живут в
  `PP\Lib\Html\Twig\SmartyCompatExtension`.
- Функции ядра (`PP\Lib\Html\Twig\CoreFunctionsExtension` и `TwigLayout`)
  зарегистрированы из коробки: `property`, `lang`, `pager`, `autopager`,
  `createpath`, `img`, `html_import`, `jquery`, `layout_var`, `pager_href`;
  модификаторы `property`, `lang`, `date_to_time`; блок `assets_apply`
  (`{% apply assets_apply %}...{% endapply %}`).
- Проектные функции/модификаторы регистрируются так же, как раньше:
  `$layout->addTemplateFunction('name', $callback)` /
  `addTemplateModifier()` — колбэки в Smarty-стиле
  `($params, &$smarty)` работают без изменений.
- Пагинация: `{{ pager({objects: ..., format: ...}) }}` и
  `{{ autopager({format: ...}) }}` рендерят `misc/pager/pages.twig`
  (байт-в-байт совместимо с рендером Smarty-версии из 3.x).

## Конвертация шаблонов: `pp templates:convert`

Команда конвертирует **исходники** Smarty 2 (`.tmpl`) в Twig (`.twig`) —
Smarty-рантайм для этого не нужен. Используйте её при переводе проекта
с pp-core 3.x на 4.x.

```bash
pp templates:convert                      # BASEPATH/local/templates рекурсивно
pp templates:convert local/templates/lt   # только поддерево
pp templates:convert --dry-run            # отчёт без записи файлов
pp templates:convert --force              # перезаписать существующие .twig
```

Каждый `foo.tmpl` конвертируется в `foo.twig` рядом с исходником.
Статусы в отчёте:

- `OK` — конвертирован полностью;
- `CHECK` — конвертирован, но есть предупреждения (например,
  `{assign}` внутри цикла: в Twig `{% set %}` локален для цикла,
  а в Smarty присваивание «протекает» наружу — если переменная
  читается после цикла, нужен ручной рефакторинг; или модификатор,
  не известный конвертеру, — убедитесь, что проект регистрирует его
  через `addTemplateModifier()`);
- `MANUAL` — есть конструкции без автоматического аналога
  (`{php}`, `{break}`/`{continue}`, `{section step=...}`).
  Такие места остаются в выводе в виде `{# UNCONVERTED: ... #}`
  с указанием файла и строки в отчёте;
- `SKIP` — `.twig` уже существует (перезапись — через `--force`).

Конвертер сохраняет байтовую совместимость вывода, включая тонкости
Smarty 2 с переносами строк после тегов и семантику `{strip}`.

Предупреждения о функциях, «не определённых в CLI» — это функции,
доступные только в веб-бутстрапе проекта: убедитесь, что они существуют
в рантайме, и игнорируйте предупреждение.

## Проверка результата

Сравнивайте рендер ключевых страниц до миграции (pp-core 3.x, Smarty)
и после (4.x, Twig): снимите HTML (`curl`) на обеих версиях и сравните.
Расхождения допустимы только в случайных значениях (nonce, csrf-токены)
и незначащих пробелах.

## Известные ограничения автоконвертации

| Конструкция | Что делать |
|---|---|
| `{php}...{/php}` | переносить логику в модуль/функцию вручную |
| `{break}`, `{continue}` | в Twig нет; переписать через `filter`/условие |
| `{section step=... / max=... / show=...}` | остаётся `{# UNCONVERTED #}`; переписать на `{% for %}` вручную |
| `{assign}` в цикле, читаемый после цикла | вынести из цикла или собрать через `layout_var` |
| `{cycle}`, `{counter}`, `{eval}`, `{fetch}`, `{html_*}` | ручной порт (используются крайне редко) |

`===`/`!==` конвертируются автоматически в twig-тест `is same as(...)`
(строгое сравнение сохраняется). `{capture name=X assign=Y}` заполняет
обе переменные (`$Y` и `$smarty.capture.X`), как в Smarty.

## Отличие: области видимости `{include}` с параметрами

В Smarty 2 из pp-core 3.x переменные, переданные в
`{include file=... var=...}`, из-за особенности реализации (`_tpl_vars` —
объект) оставались видимыми и **после** include — «протекали» в шаблоны,
рендерящиеся следом. В Twig `{% include ... with {...} %}` таких утечек нет:
переданные переменные видны только внутри включаемого шаблона.

Если проект полагается на такую утечку (сосед-шаблон читает переменную,
которую кто-то раньше передал в include), после миграции переменная станет
пустой — проверяйте такие места сравнением отрендеренных страниц.

## Ручные правки после переконвертации

`templates:convert --force` перезаписывает все `.twig`, включая портированные
вручную ({break}/{continue} и т.п.). Держите ручные правки идемпотентным
патч-скриптом рядом с шаблонами и накатывайте его после каждой
переконвертации (пример: `local/templates/twig-manual-patches.php` в проекте
sbertelecom — str_replace-патчи со статусами OK/SKIP/FAIL).
